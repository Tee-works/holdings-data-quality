## C01

**Line count matches the summary page.** Completeness, critical severity, owned by Regulatory Reporting. Source: [`controls/C01_entry_count.sql`](../controls/C01_entry_count.sql).

*What it checks.* The number of lines in the information table equals the "table entry total" declared on the summary page of the same filing.

*Why it matters.* The summary page is a control total for the table. If the two disagree, a reader cannot tell which is right without going back to the source, so totals built from the filing need checking first.

*Triage runbook.*

1. Re-run the control for the filing and note both counts from the detail column.
2. Count the lines in the extract that fed the submission; compare with both numbers.
3. If the extract matches the summary page, the information table lost lines in generation; raise with the reporting platform team.
4. If the extract matches the table, the summary page was keyed or calculated wrongly; raise with Regulatory Reporting.
5. Close when an amendment is filed or the difference is documented as explained.

## C02

**Line values add up to the summary page total.** Accuracy, critical severity, owned by Regulatory Reporting. Source: [`controls/C02_value_total.sql`](../controls/C02_value_total.sql).

*What it checks.* The sum of line values equals the "table value total" on the summary page, within the rounding that whole-unit line values can explain (half a unit per line).

*Why it matters.* The value total is the headline figure readers take from a 13F. A difference larger than rounding means the lines and the total were not produced from the same data, and one of them needs explaining.

*Triage runbook.*

1. Note the difference and its sign from the detail column.
2. Look for a single line whose value equals the difference (a dropped or duplicated line).
3. Check whether the total was taken from a different extract time than the lines.
4. Agree the corrected figure with Regulatory Reporting and decide whether an amendment is needed.
5. Close when amended or explained in the issue log.

## C03

**CUSIP is well formed with a valid check digit.** Validity, high severity, owned by Security Master. Source: [`controls/C03_cusip_check_digit.sql`](../controls/C03_cusip_check_digit.sql).

*What it checks.* Every line carries a 9-character CUSIP whose ninth character is the modulus 10 "double add double" check digit of the first eight. Written in plain SQL so it runs on any warehouse; the Python implementation is used only to test it.

*Why it matters.* A CUSIP that fails its check digit cannot be matched to the security master, so the position drops out of exposure, compliance and stewardship reports that join on it.

*Triage runbook.*

1. Take the issuer name and class from the line and look the security up in the security master.
2. If the master holds a valid CUSIP for it, the error is in the extract or a manual override; correct at source.
3. If the master holds the same invalid CUSIP, raise a security master data fix.
4. Check whether other filings use the same invalid identifier (search exceptions by entity).
5. Close when the identifier is corrected or the line is documented as a known placeholder.

## C04

**FIGI, where reported, is well formed with a valid check digit.** Validity, medium severity, owned by Security Master. Source: [`controls/C04_figi_format.sql`](../controls/C04_figi_format.sql).

*What it checks.* FIGI is optional on Form 13F. Where it is reported it must be 12 characters: a two-letter prefix without vowels, "G" in third place, eight consonants or digits, and a check digit computed like the CUSIP one over the first eleven characters. Lines without a FIGI are outside the population, so the control reports n/a when no FIGIs are reported.

*Why it matters.* An invalid FIGI breaks the cross-reference between identifiers. Teams that key on FIGI rather than CUSIP (for example, vendor data and newer reference data feeds) silently lose the position.

*Triage runbook.*

1. Compare the reported FIGI with the one held in the security master for the same CUSIP.
2. If the master value is valid, correct the extract mapping.
3. If the master value is also invalid, raise a reference data fix with the vendor feed owner.
4. Close when corrected or documented.

## C05

**Coded fields use the values the form allows.** Validity, high severity, owned by Investment Data Operations. Source: [`controls/C05_coded_values.sql`](../controls/C05_coded_values.sql).

*What it checks.* Amount type is SH or PRN; investment discretion is SOLE, DFND or OTR; put/call is empty, Put or Call.

*Why it matters.* These codes decide how a line is aggregated. An unknown discretion code drops the line from the "sole versus shared" splits used in stewardship reporting; a wrong amount type mixes share counts with bond principal.

*Triage runbook.*

1. Read the failing field and value from the detail column.
2. Find the mapping that produces the field in the reporting extract and the source value that fed it.
3. Add the missing mapping or correct the source value; never hand-edit the filing output.
4. Close when the next run passes or an amendment is filed.

## C06

**Other manager numbers refer to managers on the summary page.** Validity, medium severity, owned by Regulatory Reporting. Source: [`controls/C06_other_manager_reference.sql`](../controls/C06_other_manager_reference.sql).

*What it checks.* Every number in a line's "other manager" column is a sequence number in the same filing's list of other included managers, which sits on the summary page. A blank column, or N/A, NONE or 0, means no other manager and is not checked (SEC Form 13F FAQ 49 allows a blank or N/A).

*Why it matters.* The other manager column attributes a holding to a group entity. A number that is not in the list means the holding cannot be attributed, so entity-level views of the book are incomplete.

*Triage runbook.*

1. Note the unlisted number(s) from the detail column.
2. Compare with the list of other included managers on the filing's summary page for that quarter.
3. If an entity is missing from the list, the summary page and the table disagree; if the line carries a stale entity number, the mapping that fills the column is out of date.
4. Record which it is and close.

## C07

**Voting authority split matches shares held.** Consistency, low severity, owned by Stewardship Data. Source: [`controls/C07_voting_authority.sql`](../controls/C07_voting_authority.sql).

*What it checks.* For plain share lines, sole, shared and no voting authority together equal the number of shares. Informational: the form does not require the three columns to add up to the holding (SEC Form 13F FAQ 50a), so a difference is a question for a stewardship team, not a reporting error. Options and principal amounts are excluded.

*Why it matters.* Voting and engagement reporting reads these columns. Where they do not cover the position, the votes a firm reports controlling will not reconcile to what it holds, and someone will ask why.

*Triage runbook.*

1. Compare the voting split with the voting authority held on the proxy voting platform for the same date.
2. Shares on loan or held in accounts where voting is delegated are common, legitimate reasons; record them as explained.
3. Otherwise, find the step that fills the voting columns and check it against the position.

## C08

**No line is repeated exactly.** Uniqueness, high severity, owned by Regulatory Reporting. Source: [`controls/C08_duplicate_lines.sql`](../controls/C08_duplicate_lines.sql).

*What it checks.* No two lines in a filing agree on every field (security, class, amounts, value, discretion, other manager, put/call and voting authority). The first copy passes; each further copy is an exception and its value is the amount double counted.

*Why it matters.* An exact repeat is either two genuine holdings that happen to match on every field, or a line produced twice. Until that is established, totals that include it may count the position twice.

*Triage runbook.*

1. Confirm both lines are identical in the source extract (not just in the filing).
2. Find the join or union in the extract that produced the second copy.
3. Decide with Regulatory Reporting whether the overstatement needs an amendment.
4. Close when the extract is fixed and the next run passes.

## C09

**Each CUSIP has one issuer name within a filing.** Consistency, low severity, owned by Security Master. Source: [`controls/C09_issuer_name_per_cusip.sql`](../controls/C09_issuer_name_per_cusip.sql).

*What it checks.* All lines for the same CUSIP in a filing carry the same issuer name, compared after ignoring case, spaces and punctuation so that "APPLE INC" and "Apple Inc." agree.

*Why it matters.* Two names for one security usually means two reference data records. Reports that group by name split the position and understate the largest exposures.

*Triage runbook.*

1. List the names reported for the CUSIP (see the detail column).
2. Check the security master for duplicate records or a stale name on one record.
3. Merge or correct the records; the reporting extract should take the name from the master only.

## C10

**Lines for one security and one entity imply the same price.** Accuracy, high severity, owned by Pricing. Source: [`controls/C10_price_consistency.sql`](../controls/C10_price_consistency.sql).

*What it checks.* Within one filing, lines for the same CUSIP attributed to the same entity (the same "other manager" value) should be valued at the same price, so value divided by shares should agree. A line is an exception if its implied price differs from the median for that security and entity by more than 0.5% plus what rounding the value to a whole unit can explain. Differences between entities are expected (they can price at different times or from different sources) and are measured separately by C17. Shares only: options and principal amounts are excluded.

*Why it matters.* One entity valuing one security at two prices on the same date means a quantity or a value on at least one line does not match the rest. Reports that read different lines will disagree.

*Triage runbook.*

1. Compare the line's shares and value with the other lines for the same security and entity.
2. If the shares look wrong, check the position records; if the value looks wrong, check the price applied.
3. With two lines there is no majority, so both are flagged; establish which one is right before closing.

## C11

**Large quarter-on-quarter price moves, for review.** Accuracy, low severity, owned by Pricing. Source: [`controls/C11_price_moves.sql`](../controls/C11_price_moves.sql).

*What it checks.* For each security held in two consecutive quarters, an implied price that moves by more than a factor of three is listed for review. Stock splits and consolidations are recognised and cleared automatically: for a price that falls to roughly 1/k (or rises to roughly k times) for a whole number k of 2 or more, with the share count moving by between 0.67k and 1.5k the other way, the move is recorded as a likely k-for-1 split (or 1-for-k consolidation). The tolerance allows for the position itself growing or shrinking in the same quarter. Genuine large moves (takeovers, distressed securities, momentum stocks) will appear here every quarter; that is expected.

*Why it matters.* A price that moves threefold in a quarter is a real market event, a corporate action the reference data must reflect, or an error in shares or value. Telling these apart early keeps performance and quarter-on-quarter reporting honest.

*Triage runbook.*

1. Check corporate action records for a split, consolidation, spin-off or rights issue in the quarter.
2. If there was one, confirm the security master and position history reflect it, then mark explained.
3. If not, compare the quarter-end market price with the implied price in both quarters to see which side moved.
4. Record the explanation (market move, corporate action or data error) and close.

## C12

**Report scale is consistent with the previous quarter.** Consistency, critical severity, owned by Regulatory Reporting. Source: [`controls/C12_portfolio_scale.sql`](../controls/C12_portfolio_scale.sql).

*What it checks.* Guards the unit rule. Two tests against the previous quarter: total value must stay within a factor of two, and the median price move across securities held in both quarters must stay within a factor of two. A whole report filed in thousands when it should be in dollars (or the reverse) moves both by about a thousandfold. The detail shows the raw ratio before unit conversion, so a reviewer can see the conversion doing its job on the 2022 to 2023 change.

*Why it matters.* A unit error misstates every value in the report by a factor of a thousand, and every downstream consumer of the data (including commercial data vendors that redistribute 13F data) inherits it.

*Triage runbook.*

1. Compare a handful of line values with known quarter-end prices to establish the unit actually used.
2. Check the filing date against the 3 January 2023 rule (dollars from then on).
3. If the filing used the wrong unit, raise with Regulatory Reporting for an amendment.
4. If the move is real (a large transfer of assets in or out), record the business event and close as explained.

## C13

**Report filed by the 45-day date.** Timeliness, medium severity, owned by Regulatory Reporting. Source: [`controls/C13_filed_on_time.sql`](../controls/C13_filed_on_time.sql).

*What it checks.* Original reports (not amendments) carry an EDGAR filing date no later than 45 days after the end of the quarter, moved to the next business day when day 45 is a weekend or a US federal holiday (SEC Form 13F FAQ 25). The filing date is the one EDGAR records; this control does not know about any arrangement with the SEC that changes it.

*Why it matters.* Filing dates are part of a reporting timetable that data quality depends on: when a report lands later than planned, it is worth knowing which step moved.

*Triage runbook.*

1. Confirm the filing date and acceptance time on EDGAR.
2. Check the computed date against the SEC calendar for that quarter.
3. Record what is known about the timing and close.

## C14

**Values and quantities are present and positive.** Validity, medium severity, owned by Investment Data Operations. Source: [`controls/C14_positive_amounts.sql`](../controls/C14_positive_amounts.sql).

*What it checks.* Every line has a value and a share or principal amount, and both are greater than zero. Form 13F lists long positions, so a zero or negative amount is unusual and worth a look.

*Why it matters.* A zero or missing amount usually means a closed position leaked into the extract, or a quantity was lost. Either way the line distorts counts of holdings and any per-share calculation.

*Triage runbook.*

1. Check the position record for the security and date.
2. If the position was closed before quarter end, remove it from the extract scope.
3. If the position is open, find where the quantity or value was lost.

## C15

**Implied share prices are plausible.** Accuracy, medium severity, owned by Pricing. Source: [`controls/C15_price_plausible.sql`](../controls/C15_price_plausible.sql).

*What it checks.* Value divided by shares lies between 1 cent and 2 million dollars. Catches a value or quantity off by orders of magnitude on a single line, which line-level and total checks can miss. Securities written down to near zero (for example, suspended listings) also appear here, and are expected to be closed as explained.

*Why it matters.* An implausible price on one line misstates that position by orders of magnitude. For a large position, that alone can move headline exposure figures.

*Triage runbook.*

1. Compare the implied price with the quarter-end market or evaluated price.
2. If the security is suspended or written down, confirm the valuation policy applied and mark explained.
3. Otherwise identify whether shares or value is wrong and raise with the owning team.

## C16

**Warehouse reconciles to the source document (TrueSet).** Completeness, critical severity, owned by Data Engineering. Source: [`controls/C16_load_reconciliation.sql`](../controls/C16_load_reconciliation.sql).

*What it checks.* At load time every information table is read twice, by the main parser and by an independent reader that shares no code with it (a different XML library and XPath), and the warehouse is reconciled against the independent reading with TrueSet, an open-source data quality library: by count, then line by line on identifiers, values and codes. Keys missing on either side, duplicated keys and changed values are all reported. A document that cannot be read at all is reported here too, and the rest of the run carries on.

*Why it matters.* Every other control assumes the warehouse holds exactly what was filed. If parsing or loading drops, duplicates or alters lines, the other controls check the wrong data, and nothing else would show it.

*Triage runbook.*

1. Read the TrueSet message and observed counts in the detail column (missing, extra, mismatched or duplicated keys), or the parse error.
2. Pick one failing line key and compare the XML element with the warehouse row to see which reader is wrong.
3. Fix the reader, add the case to the tests, and re-run `hdq build`.
4. Treat other control results for the filing as unreliable until this passes.

## C17

**Group entities value each security at a consistent price.** Consistency, low severity, owned by Pricing. Source: [`controls/C17_cross_entity_pricing.sql`](../controls/C17_cross_entity_pricing.sql).

*What it checks.* For securities reported under more than one entity (the "other manager" column), each entity's implied price (its total value over its total shares) is compared with the median across entities in the same filing. An entity-security pair more than 2% away is listed. Informational: entities in a group can legitimately value at different times of day or from different sources. The control measures how often that happens and by how much, which is the first question in any pricing consistency review.

*Why it matters.* When one firm reports the same security at different prices, group-level exposure depends on which entity's figures are used, and the difference flows into any aggregate built from the filing.

*Triage runbook.*

1. Check whether the entities concerned use a different pricing point or source by policy.
2. If they do, record the policy as the explanation and close; if they should not differ, raise with the pricing team.
3. {'Look for a pattern': 'one entity consistently away from the others points to a policy difference rather than a data error.'}

## C18

**A new-holdings amendment adds lines rather than repeating the report.** Uniqueness, high severity, owned by Regulatory Reporting. Source: [`controls/C18_new_holdings_amendment.sql`](../controls/C18_new_holdings_amendment.sql).

*What it checks.* A 13F-HR/A of type NEW HOLDINGS adds lines to the quarter's report; a full replacement should be a RESTATEMENT. If more than half of an amendment's lines match a line in the base report on CUSIP, shares and value, the amendment is probably a full report filed under the wrong type, and adding it would count those holdings twice. Only NEW HOLDINGS amendments are in scope.

*Why it matters.* The staging layer adds NEW HOLDINGS amendments to the base report. If an amendment is really a restatement, every total for the quarter is inflated by the repeated lines.

*Triage runbook.*

1. Open the amendment and the base report on EDGAR and compare line counts.
2. If the amendment is a full report, treat it as a restatement for this quarter (record the decision) so staging stops adding it.
3. If the matching lines are genuinely new positions that happen to match, record that and close.
